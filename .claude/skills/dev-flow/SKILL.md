# 変更を計画から PR まで進める

メインのセッションは調整役として、計画、指示、統合、文書を受け持つ。コードは係に書かせ、検証はスクリプトに、判定はレビュー係に任せる。

この手順は taklog（技術ブログのリポジトリ）の dev-flow を写したもの。taklog は手順の外の操作を hook で止めるが、このリポジトリに hook はない。下の決まりは、メインのセッションが自分で守る。

| 係 | 定義 | モデル | 受け持つもの |
| --- | --- | --- | --- |
| 探す係 | `explorer` | haiku・low | ファイル、行、抜粋の一覧。結論は出さない |
| 作る係 | `builder` | opus・medium | `src/` のコード、`e2e/` のブラウザのテスト、`scripts/` のスクリプト |
| CSS の各係 | css-change のスキル | 読む係 haiku、実装係 opus・medium、判断する係 opus・high | CSS |
| レビュー係 | `reviewer` | fable・medium | ブランチの差分全体の判定。読むだけ |
| 助言役 | `/advisor fable` | fable | 会話の全文を読んで助言する。難しいタスクのときだけ、ユーザーがそのセッションで有効にする |

Fable を使うのはレビュー係と、ユーザーが有効にした助言役だけにする。サブスクリプションでは、Fable は週の利用枠を Opus より速く使い、使えるのも枠の一部に限られるため。

メインが自分で書くのは、文書と設定（`.md`、`.claude/` の中、設定ファイル）と、`src/` のすでにある 1 ファイルへの、1 ターンで合わせて 10 行までの変更にする。`src/` の新しいファイル、合わせて 10 行を超える変更、複数のファイルにまたがる変更、`e2e/` と `scripts/` のコードは、作る係に任せる。CSS（`.css`、`.astro` の `<style>` と `style` 属性）は、1 行でも css-change の手順に任せる。

## 手順

1. 計画を立てる。目的、受け入れの条件（どのテストやコマンドが通れば完了か）、変えるファイルと担当の係を決める。変えるファイルが分からなければ、探す係に対象を渡して場所の一覧をもらう。
   - 助言役が有効なら、複数のファイルにまたがる計画は、決める前に助言役に相談する。有効でなく、設計の判断が難しいと考えたら、`/advisor fable` を有効にするかをユーザーに聞く。
   - 完了条件: 計画をユーザーに見せ、作業ブランチ、コミット、PR まで進めてよいかの了承を得ている。
2. 書かせる。作業ブランチを切ってから、担当ごとに進める。
   - `src/`、`e2e/`、`scripts/` のコード: 作る係に、下の「作る係への指示」の形で渡す。
   - CSS: css-change のスキルの手順。
   - 文書、設定、小さな修正: メインが書く。日本語の文書は japanese-tech-writing に沿って書き、yomiyasu で推敲する。
   - 係の報告にある「担当の外で要る変更」は、その担当の係に回す。「消したいコード」は、1 件ずつ、何を消すか（ファイルとコード）を示してユーザーに確かめる。
3. コミットする。差分から消えた行（`git diff` の `-` の行）を確かめ、理由のコメントが付いたコードやユーザーが決めた実装が消えていないことを見てからコミットする。メッセージは AGENTS.md の決まりで書く。
4. 検証する。`pnpm verify` をバックグラウンドで実行する。記録は `.claude/logs/receipts/<ブランチ名の / を - にしたもの>.json` に残る。
   - 失敗したら、担当の係に直させて手順 3 に戻る。同じ失敗が 2 回続いたら、直させる前に助言役に相談する（助言役が有効でなければ、有効にするかをユーザーに聞く）。
   - 完了条件: 記録の `ok` と `clean` が真で、`commit` が HEAD と同じ。
5. 助言役が有効なら相談する。完了と判断する前に、変更の要約と検証の記録を踏まえて、見落としがないかを助言役に聞く。助言で直すものがあれば、手順 2 に戻る。
6. レビューさせる。レビュー係に、下の「レビュー係への指示」の形で渡す。会話の内容や係の報告は渡さない（レビューを独立させるため）。Fable の利用枠を使い切って呼べないときは、呼び出しで `model: opus`、`effort: xhigh` を渡してレビュー係を呼ぶ。
7. 直させる。判定が `changes` なら、指摘ごとに担当の係に直させ、手順 3 から 6 を繰り返す。2 回目からのレビューの指示には、前回の判定のファイルを添える。
   - 指摘に、理由のコメントが付いたコードやユーザーが決めた実装を消す内容があれば、直さずに 1 件ずつユーザーに確かめる。
   - 直してレビューに見せ直すのを 2 周しても `approve` にならなければ、止めて、残った指摘と双方の言い分をユーザーに見せて判断を仰ぐ。
   - 完了条件: 判定が `approve` で、その `commit` が HEAD と同じ。
8. PR を作る。検証の記録（`ok` と `clean` が真）とレビューの判定（`approve`）の `commit` が、どちらも HEAD と同じであることを確かめる。そのうえで `git push -u origin <ブランチ>` の後に `gh pr create` を実行する。PR の説明文には、変えた内容、検証の記録の結果、レビューの判定、ブラウザで確かめていない項目を書く。

## 作る係への指示

```
目的: <何のための変更か>
受け入れの条件:
- <足すテストと、確かめる振る舞い>
- <通すコマンド（pnpm test、必要なら pnpm build や pnpm test:e2e）>
担当（書いてよいファイル）: <ファイルの一覧>
触らないファイル: <あれば。CSS とスライドの原稿は常に担当の外>
材料: <探す係の一覧、関係する規約、決まったこと>
```

## レビュー係への指示

```
ブランチ: <ブランチ名>
基準: origin/main
前回の判定: <2 回目からは .claude/logs/reviews/<名前>.md。1 回目は「なし」>
```
