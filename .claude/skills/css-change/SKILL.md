# CSS を書く・直す

CSS のガイドラインを通読した読む係（Haiku）のチェック表をもとに、実装係（Opus・medium）が書き、判断する係（Opus・high）が照合する。メインのセッションは CSS を書かず、CSS を変える書き込みは実装係に任せる。

この手順は taklog（技術ブログのリポジトリ）の css-change を写したもの。taklog は手順の外の書き込みを hook で止めるが、このリポジトリに hook はない。メインのセッションが自分で守る。

## どちらの手順で進めるか

- **通読する手順**: 新しく CSS を書くとき。既存の CSS に、いまの CSS にない種類の書き方（プロパティ、セレクタ、@ 規則、単位、関数、カスタムプロパティ）を加えるとき。
- **差分だけの手順**: 既存の宣言の値だけを変えるとき。コメントや名前だけを変えるとき。宣言を消すとき。判断する係の指摘を直すとき。

どちらか迷ったら、通読する手順にする。差分だけの手順の途中で、新しい種類の書き方が要ると分かったら、通読する手順に切り替える。

## MCP がつながらないとき

ガイドラインの MCP は、プラグインの `mcp__plugin_recss-guideline_recss-guideline__*` と、`mcp__recss-guideline__*` の 2 つの名前で入っている。プラグインのほうは、接続が切れていることがある。

- 読む係と実装係は、定義に「片方につながらなければ、もう片方を使う」と書いてある。判断する係はプラグインの定義で書き換えられないので、呼ぶたびに依頼文へ次を書く: 「ガイドラインの MCP は 2 つの名前で入っている。片方につながらなければ、もう片方の同じ名前のツールを使う。`lint_css` をかけられなかったら、そのことを結果の冒頭に書く」
- `lint_css` をかけていない照合は、通ったとみなさない。MCP につながってから、判断する係にかけ直させる。

## 通読する手順

1. 範囲と作業名を決める。対象のファイル（新しく書くなら、書く内容と置き場所）を列挙し、作業名を英語の kebab-case で付ける。1 回の対象は、1 つのコンポーネントか数ファイルにする。それより大きいときは分けて、この手順を繰り返す。
2. 章を選ぶ。MCP の `list_chapters`（使えないときはガイドラインのスキルの「章の索引」）の読む条件を対象に当て、関係する章を決める。「常に読む」の章は必ず含める。当たるか迷った章は「読む」にする。読む係は並列に動くので、章を足しても待ち時間はほとんど増えない。一方、外した章に当たる書き方が実装に入ると、追加の通読、修正、照合のやり直しが 1 周増える。文字を含む要素や配置を書くなら、コンポジションの章とタイポグラフィの章は当たるものとして読む。
   - 完了条件: 索引のすべての章が、「読む」か「外す（理由）」のどちらかになっている。外す理由は、対象の CSS にその章の扱う書き方が出てこないと言い切れるものに限る。
3. 読了表を作る。関係する章のすべての節を、ページID、タイトル、字数とともに `.claude/recss-checklists/<作業名>/plan.md` に並べ、合計 8 万字以内のまとまりに分ける（章の途中で分けてよい）。外した章とその理由も書く。
   - 完了条件: 関係する章の節が、1 つ残らず読了表のどれかのまとまりにある。
4. 通読させる。まとまりごとに 1 つの読む係（`recss-reader`）を呼ぶ。同時に動かせる読む係は 20 体までなので、最初の 20 のまとまりを 1 つのメッセージで呼び、21 番目からは、戻った読む係の数だけ呼び足す。依頼文には、作業名、対象、読む節、チェック表のパス（`.claude/recss-checklists/<作業名>/<まとまりの番号>.md`）を書く。
   - 読む係はバックグラウンドで動き、1 体戻るたびにメインのセッションに報告が届く。全員がそろうまでは、届いた報告の読了の数と欠けの確認を確かめ、呼び足しが要れば呼んで、ターンを終える。報告のたびに途中経過をユーザーに書かない。
   - 完了条件: すべての読む係が戻り、読了の節の数が割り当てと一致し、どの読む係も欠けの確認を済ませている。読めなかった節は、別の読む係に割り当て直す。
5. 書かせる。実装係（`css-implementer`）に、作業の内容、対象のファイル、チェック表のディレクトリ（`.claude/recss-checklists/<作業名>/`）を渡す。
6. 照合させる。判断する係（`recss-guideline:recss-guideline-judge`）を `model: opus`、`effort: high` で呼ぶ（判断する係はプラグインの定義なので、呼ぶたびに渡す）。依頼文には次を書く。
   - 対象の CSS（実装係が変えたファイル）、関係する章、読了表のパス、チェック表のディレクトリ、プロジェクトの規約（`.claude/rules/css.md`）
   - 読む係の結果はチェック表のファイルにあるので、すべて読むこと
   - 読む係が、節ごとにルールの欠けを `search_rules` で確かめてある。判断する係の手順 1 は、読了表のすべての節にチェック表があることを確かめるだけでよいこと
   - 実装で、手順 2 で外した章に当たる書き方が加わっていないかを確かめ、加わっていれば、その章を報告すること
   - 「MCP がつながらないとき」の決まり
   - 完了条件: 判断する係が、すべての指摘を「確認済み」「却下（理由）」「食い違い」に振り分けている。外した章に当たる書き方が加わっていれば、その章の節だけを手順 3 と 4 で読ませ、照合させ直してある。
7. 直させる。確認済みの違反があれば、下の差分だけの手順の 2 から 3 で直させる。作業名は同じものを使う。
   - 完了条件: 確認済みの違反が残っていない。直さないと決めたものは、理由をユーザーに確かめてある。
8. 報告する。読了表、確認済みの違反と直し方、食い違い、却下した指摘、ブラウザで確かめていない項目を、ルールID を添えて書く。判断する係が振り分けた結果は、そのまま載せる。
9. 片付ける。`.claude/recss-checklists/<作業名>/` を消す。

## 差分だけの手順

1. 変える箇所を書く。`.claude/recss-checklists/<作業名>/plan.md` に、変える箇所（ファイルと行）と、差分だけの手順を選んだ理由を書く。通読する手順の続きで指摘を直すときは、そのディレクトリに書き足す。
2. 書かせる。実装係に、作業の内容、対象のファイル、チェック表のディレクトリを渡す。指摘を直すなら、判断する係の確認済みの違反も渡す。
3. 照合させる。判断する係を `model: opus`、`effort: high` で呼ぶ（判断する係はプラグインの定義なので、呼ぶたびに渡す）。依頼文には次を書く。
   - 実装係が変えた箇所（ファイルと行）。指摘を直したときは、前回の確認済みの違反
   - 判断する係の手順の 1 と 2（チェック表の欠けの確認、章のルールの読み直し）は行わず、手順 3 の見直しは変えた箇所に絞ること
   - 変えた箇所に当たるルールを `search_rules` と `get_rule` で引いて確かめること。指摘を直したときは、指摘ごとに解消したかを確かめること。`lint_css` をかけること
   - 「MCP がつながらないとき」の決まり
   - 完了条件: 確認済みの違反が残っていない。新しい種類の書き方が加わっていると判断する係が報告したら、通読する手順に切り替えてある。
4. 報告する。変えた箇所、照合の結果（ルールID つき）、ブラウザで確かめていない項目を書く。
5. 片付ける。通読する手順の続きでなければ、`.claude/recss-checklists/<作業名>/` を消す。
