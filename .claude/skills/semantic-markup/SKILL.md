# Semantic Markup

意味を伝え、すべてのユーザーに奉仕し、Web プラットフォームを尊重する HTML を書く。

## このスキルを使うとき

- コンポーネントやページセクションを新規作成するとき
- マークアップのアクセシビリティとセマンティクスをレビューするとき
- ネイティブ HTML 要素と ARIA 属性のどちらを使うか判断するとき
- 適切な見出し階層を設計するとき
- インタラクティブ要素をアクセシブルにするとき
- 適切なラベリングとエラーハンドリングを備えたフォームを構築するとき
- レスポンシブなテーブルを作成するとき

## 基本原則

### コンテンツのリアリズム

デザインのコンテンツは理想化されている。実際のコンテンツは雑然としている。常に以下を想定すること。

- 長い文と長い単語
- 異なるアスペクト比・サイズの画像
- 多言語対応（予定がなくてもブラウザ翻訳でユーザーが翻訳できる）
- 長さや構造が動的に変化するコンテンツ

デザインツールで綺麗に見えるものではなく、現実のコンテンツを適切に扱えるコンポーネントを構築すること。

### ランドマーク優先の設計

個別のコンポーネントに着手する前に、ページ全体の構造を検討する。これにより以下が可能になる。

- 支援技術ユーザーのための主要なランドマークを特定する
- ドキュメント全体の見出し階層を計画する
- 要素選択について十分な情報に基づいた判断を下す
- ランドマークの過剰使用を避ける（過剰になるとランドマークの有用性が低下する）

### ネイティブ要素を ARIA より優先

ARIA の第一原則に従う：必要なセマンティクスと振る舞いをネイティブ HTML 要素が提供しているなら、汎用要素に ARIA を追加するのではなくネイティブ要素を使用すること。

**危険信号**: 複雑でないコンポーネントにおいて、`div` の多用と ARIA の多用が同時に見られる場合、基礎ではなくパッチに頼っている兆候である。

### 視覚的階層とセマンティック階層の分離

視覚的なスタイルとセマンティックな意味は関連するが、結合されるべきではない。CSS クラスがその橋渡しをする。

- ドキュメント構造に基づいて適切な見出しレベルを使用する
- 視覚的な見た目（サイズ、ウェイト、色）は CSS クラスで制御する
- セマンティックレベルに関係なく一貫した視覚的扱いを提供するために `.u-Heading-XXL` のようなユーティリティクラスを作成する

## ドキュメント構造

### ランドマーク要素

ページ構造を伝えるためにランドマーク要素を使用する。

| 要素       | 使用する場面                 | 備考                                                                                               |
| ---------- | ---------------------------- | -------------------------------------------------------------------------------------------------- |
| `header`   | ページまたはセクションの冒頭 | 異なるコンテキストで複数回出現可能                                                                 |
| `footer`   | ページまたはセクションの末尾 | 連絡先情報、著作権、関連リンク                                                                     |
| `nav`      | ナビゲーションセクション     | ラベル必須。ラベルに「ナビゲーション」を含めない（スクリーンリーダーが自動でアナウンスするため）     |
| `main`     | 主要コンテンツ               | ページ内に 1 つのみ                                                                                |
| `aside`    | 間接的に関連するコンテンツ   | サイドバー、プルクォート、広告                                                                     |
| `search`   | 検索機能                     | 検索フォームを含む。検索結果ではない                                                               |
| `form`     | ユーザー入力                 | `aria-labelledby` または `aria-label` でラベル付けされた場合のみランドマークになる                  |
| `article`  | 自己完結したコンテンツ       | シンジケートされるか、単独で意味を成すもの                                                         |
| `section`  | テーマ的なグループ化         | ラベル付けされた場合のみランドマークになる                                                         |

### `section` 要素

アクセシブルな名前のない `section` は、セマンティック的には `div` と同等である。`section` を使用する際は以下に注意する。

- `aria-labelledby` で見出しと関連付ける
- これにより有効なランドマーク `region` に変わる
- 意味のあるラベルを付けられないなら、`section` が適切な選択かどうかを再考する

### `article` 要素

ブログ記事だけに限定して考えないこと。単独で意味を成す自己完結したコンテンツに使用する。

- ブログ記事やニュース記事
- 投稿へのコメント
- 一覧中の商品カード
- ソーシャルメディアの投稿
- フォーラムの投稿

**テスト**: そのコンテンツを取り出して、周囲のコンテキストなしに別の場所に配置しても意味が通るか？

### `address` 要素

しばしば誤解される。HTML 仕様より：

> `address` 要素は、最も近い `article` または `body` 要素の祖先についての連絡先情報を表す。

著者やオーナーの連絡先情報に使用する。一般的な住所には使用しない。郵便住所には、コンテキストに応じた標準的な `<p>` や構造化マークアップを使用する。

### 見出し

#### 見出し階層

論理的な見出し構造を維持すること。

- ページごとに `h1` は 1 つ（通常メインタイトル）
- レベルを飛ばさない（`h1` → `h3` は不可）
- 見出しはアウトラインを形成する。順番に読んだとき意味が通ることを確認する

#### コンポーネント内の見出し

見出しを含む再利用可能なコンポーネントでは以下を考慮する。

- **見出しレベルを設定可能にする** — コンポーネントは異なるコンテキストに配置される可能性がある
- **妥当なデフォルト値を提供する** — すべてのコンテンツ作成者が見出し階層を理解しているわけではない
- **継承を考慮する** — 汎用コンポーネントが特殊化される。見出し設定はその流れに沿うべき

パターン例：

```
Card（汎用） → 見出しレベル設定可能、デフォルト h3
  └─ ProductCard（特殊化） → 設定を継承、既知のコンテキストに基づいてデフォルト設定可能
       └─ h2 セクション内で使用 → 見出しレベルを h3 に設定
```

#### セマンティック見出しなしの視覚的見出し

テキストが見出しのように見えるが、セマンティック的には見出しであるべきでない場合がある。ドキュメントアウトラインに影響を与えずに見出し風のスタイルを適用するには CSS クラスを使用する。

```html
<p class="-heading--lg">見出しのように見えるテキスト</p>
```

## リスト

### リストを使うべきとき

アイテム数を知ることがユーザーの役に立つ場合にリストが最も有用である。

- ナビゲーションメニュー（選択肢はいくつ？）
- 検索結果（何件ヒット？）
- 画像ギャラリー（画像は何枚？）
- プロセスの手順

判断のための問い：

- これらのアイテムは本当に同格か？
- 1 つ取り除いたら他が不完全に感じられるか？
- 暗黙的に「ここに N 個のものがある」と伝えているか？

### リストの種類

| 種類   | 使用場面                     | 例                                     |
| ------ | ---------------------------- | -------------------------------------- |
| `ul`   | 順序のないコレクション       | ナビ項目、検索結果                     |
| `ol`   | 順序付きの手順やランク付き   | レシピ、手順書、トップ 10              |
| `dl`   | 用語と説明のペア             | 用語集、メタデータ、キー・バリューペア |
| `menu` | ツールバーのコマンド         | アクションボタン（ナビゲーションではない）|

**`ol` の属性**: カウントダウン形式（例：10 位から 1 位）のリストには `reversed` を使用する。特定の値から番号を開始するには `start` を使用する。いずれもネイティブ HTML であり、JavaScript は不要。

### 定義リスト

見過ごされがちで、`details/summary` と混同されやすい。`dl` の用途：

- 用語集の定義
- メタデータ表示（ラベル：値 のペア）
- 1 つ以上の説明を持つ任意の用語

注意: 単一の `dt` に対して、複数の関連する説明のために複数の `dd` 要素を使用可能。

## インタラクティブ要素

### ボタン vs リンク

伝統的なルール: ボタンはアクションを実行し、リンクは場所へ移動する。

**プログレッシブ・エンハンスメントの観点**: JavaScript が失敗したときに URL が意味のあるフォールバックを提供する場合、アクション的なインタラクションにもリンクは有効。

| インタラクション                 | デフォルトの選択 | リンクを検討する場合                                 |
| -------------------------------- | ---------------- | ---------------------------------------------------- |
| 「もっと見る」コンテンツ表示     | `button`         | URL パラメータでサーバーサイドのコンテンツ読み込み可 |
| 表示切替（グリッド / リスト）    | `button`         | URL で表示設定を保持可能                             |
| クリップボードにコピー           | `button`         | コピーされるコンテンツが共有可能な URL               |
| タブ選択                         | `button`         | URL で特定タブのコンテンツを読み込み可能             |

**判断の鍵**: JavaScript が失敗したとき何が起こるか？ URL がグレースフルデグラデーションを提供するなら、リンクのほうが適切な場合がある。

### `details` / `summary` パターン

プログレッシブ・ディスクロージャーに使用する。

- FAQ セクション
- 展開可能なコンテンツセクション
- 折りたたみ可能なナビゲーション

適切な見出し構造や定義リストの代替としては使用しない。

## フォーム

### `fieldset` / `legend` によるグループ化

テーマ的なグループ化にのみ使用する。レイアウト目的では使用しない。

- 住所フィールド
- 個人情報セクション
- プライバシー / 同意チェックボックス
- 支払い情報

利点：

- プログレッシブ・ディスクロージャーが可能（ユーザーが前のセクションを完了したら次を表示）
- 圧迫感の軽減（「フォームフィールドの壁」を回避）
- スクリーンリーダーユーザーにコンテキストを提供

`legend` はアクセシブルな名前を提供しつつ視覚的に非表示にできる。

### ラベル

**常に `label` 要素を使用する。例外なし。**

- デザイン上必要な場合、視覚的に非表示のラベルは許容される
- ラベルの代わりにプレースホルダーテキストに依存してはならない
- 適切な `label` 要素が使える場合に `aria-label` を使用してはならない

プレースホルダーが失敗する理由：

- 入力時に消える（認知的課題、ストレス、注意散漫時に問題）
- コントラストが低いことが多い
- 永続的な識別を提供しない

### エラーメッセージ

現在のベストプラクティス（`aria-errormessage` のブラウザサポートの不足を踏まえて）：

- 無効な入力に `aria-invalid="true"` を設定する
- `aria-describedby` でエラーメッセージを関連付ける
- エラーメッセージは実行可能であること（問題を述べ、かつ修正方法を案内する）
- 動的エラー（blur 時に表示）の場合、エラーコンテナに `aria-live` を検討する

```html
<label for="email">メールアドレス</label>
<input
  type="email"
  id="email"
  aria-invalid="true"
  aria-describedby="email-error"
/>
<p id="email-error" class="error">
  有効なメールアドレスを入力してください（例: name@example.com）
</p>
```

## テーブル

### テーブルを使うべきとき

データが両方の次元で意味のある関係を持つ場合にテーブルを使用する。

- データを行と列の両方で提示する必要がある
- ヘッダーとデータの間に明確な関連がある
- 各行が同じカラムを持つ
- 各カラム内のデータが同じ種類である

### テーブルを使うべきでないとき

- 単純なリスト（1 次元）
- キー・バリューペア（`dl` を使用）
- フォームレイアウト
- 階層的データ（ネストしたリストを使用）

### テーブルのセマンティクスのベースライン

常に以下を含めること。

- `caption` — テーブルの目的を説明する
- `thead`, `tbody`, `tfoot` — 構造的グループ化
- `scope` 付きの `th` — ヘッダーセルとその方向を識別する

### レスポンシブなテーブル

優先順位の高い順：

1. **非必須カラムの非表示** — ユーザーは主要な情報を得られる。完全なテーブルを表示するボタンを提供する
2. **水平スクロール** — セマンティクスは保持されるが、運動機能に課題のあるユーザーには困難な場合がある
3. **コンポーネント複製（モバイルでカード表示）** — 最後の手段。両方のバージョンでアクセシビリティを維持すること

注意: モダンブラウザ（Safari 含む）は `display: grid` や `display: flex` を適用してもテーブルのセマンティクスを除去しなくなっており、新しいレスポンシブの可能性が広がっている。

## コードレビューチェックリスト

マークアップをレビューする際に確認すること。

### 良い兆候

- ランドマーク要素が適切に使用されている
- 論理的な見出し階層がある
- ネイティブのインタラクティブ要素（`button`, `a`）が正しく使用されている
- フォームに適切なラベルと `fieldset` がある
- テーブルに完全なセマンティック構造がある
- ARIA が控えめかつ正確に使用されている

### 警告の兆候

- 複雑でないコンポーネントでの `div` の多用
- ネイティブセマンティクスの欠如を補うための ARIA 属性
- ラベルとしてのプレースホルダー使用
- 構造ではなく視覚的なサイズで選ばれた見出しレベル
- `button` や `a` の代わりにクリックハンドラー付きの汎用要素
- レイアウト目的のテーブル
- 欠落したフォームラベル
